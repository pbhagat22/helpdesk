# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

The code is organized by feature package under `com.example.helpdesk`: `user`, `ticket` (tickets, comments, and publishing ticket events), `activity` (the Kafka consumer that builds ticket history), `security` and `common` (exceptions and the global error handler). Each feature is layered Controller → Service → Repository:

- **Controllers** only handle HTTP. They take and return DTO records (`Create*Request`, `Update*Request`, `*Response`) and never expose JPA entities. Request bodies are checked with `@Valid` against Bean Validation annotations on the request records.
- **Services** own the transactions (`@Transactional(readOnly = true)` at class level, overridden on write methods) and convert entities to DTOs *inside* the transaction. `spring.jpa.open-in-view=false` is set, so lazy relationships read outside a service method throw `LazyInitializationException` instead of running hidden queries.
- **Repositories** are Spring Data interfaces. `TicketRepository.search` is one JPQL `@Query` where a null parameter means "no filter on this". Use that pattern rather than adding a derived method per filter combination. List queries use `@EntityGraph` to fetch `reporter`, `assignee` or `author` in the same query, which avoids N+1 queries. Keep this when adding list queries.
- **Entity relationships** are `@ManyToOne(fetch = LAZY)` and one-directional. Comment → Ticket has no collection on `Ticket`; comments are loaded with `CommentRepository`.
- **Errors:** services throw `NotFoundException` (404), `ConflictException` (409) or `BadRequestException` (400, for business rules) from `common`. `GlobalExceptionHandler` maps them, plus validation and Spring MVC errors, to RFC 9457 `ProblemDetail` JSON. Validation failures add an `errors` field→message map. Don't use `@ResponseStatus` on exceptions or return error bodies from controllers.
- **Security** (`security` package) uses stateless JWT bearer tokens with CSRF off and no session. HTTP Basic is not enabled.
  - `POST /api/auth/login` (`TokenService`) checks email and password once, using a `DaoAuthenticationProvider` over `HelpdeskUserDetailsService` and the `{bcrypt}` hash in `users.password_hash`. It returns an HS256 JWT signed by Spring's `JwtEncoder`. Claims: `iss=helpdesk`, `sub=<user id>`, `email`, `role`, and an expiry (`helpdesk.jwt.ttl`, default 1h).
  - Other requests send `Authorization: Bearer <token>`. The OAuth2 resource server checks the signature, expiry and issuer, and `SecurityConfig.toAuthentication` turns the claims into a `HelpdeskUserDetails` principal **without a database lookup**. A role change or deleted user therefore only takes effect when the token expires.
  - The signing key comes from `HELPDESK_JWT_SECRET` (`helpdesk.jwt.secret`, at least 32 bytes). If it's unset, a random key is generated at startup (logged as a warning), so tokens die on restart. That's fine for dev and tests; production must set it.
  - Controllers take `@AuthenticationPrincipal HelpdeskUserDetails me` and pass `me.getId()` or `me` to services, so who is acting (reporter, author) always comes from the token, never from the request body. `POST /api/auth/register` (self sign-up as CUSTOMER), `POST /api/auth/login`, `/actuator/health/**` and `/error` are public; everything else requires authentication.
- **Authorization** happens in two places:
  - *Role rules* use `@PreAuthorize("hasAnyRole(...)")` on controller methods (`@EnableMethodSecurity`). Creating users and changing a user's role (`PATCH /api/users/{id}` with `{"role": ...}`) are ADMIN only; listing or getting users and `PATCH /api/tickets/{id}` are AGENT or ADMIN. `UserService.changeRole` rejects an admin changing their **own** role (400), so at least one admin always remains. A new role only reaches the user's JWT at their next login.
  - *Ownership rules* depend on data, so they live in services, which receive the `HelpdeskUserDetails`. Customers only see and comment on tickets they reported. Someone else's ticket gives **404, not 403**, so its existence isn't revealed. `TicketService.list` forces `reporterId` to the customer's own id.
- **Security errors** (401/403) go through `SecurityProblemHandler`, which hands them to MVC's `handlerExceptionResolver`, so `GlobalExceptionHandler` renders them as ProblemDetail like everything else. It needs explicit `AuthenticationException` and `AccessDeniedException` handlers; without them the catch-all `Exception` handler would turn a `@PreAuthorize` denial into a 500.
- **Bootstrap admin:** `AdminBootstrap` (an `ApplicationRunner`) creates an ADMIN at startup from `helpdesk.admin.email` and `helpdesk.admin.password` (`AdminProperties`, set with the `HELPDESK_ADMIN_EMAIL` and `HELPDESK_ADMIN_PASSWORD` environment variables) if that email doesn't exist. Several instances starting together may race; the loser's `ConflictException` / `DataIntegrityViolationException` is caught and logged, not allowed to stop startup. `compose.yaml` sets dev values for the `app` service, including `HELPDESK_JWT_SECRET`. With `spring-boot:run`, pass them as environment variables. Real credentials never go in committed files.

- **Kafka events:** `TicketService` publishes a `TicketEvent` (`eventId`, `type` from `TicketEventType`, `ticketId`, `actorId`, `occurredAt`, a `details` string map) through Spring's `ApplicationEventPublisher` for every *real* change: created, status or priority changed (`from`/`to`), assigned, commented. Setting a field to its current value publishes nothing. `TicketEventPublisher` forwards events with `@TransactionalEventListener`, i.e. only after the DB commit, to the topic `helpdesk.ticket-events` (3 partitions, created at startup by a `NewTopic` bean). Events are JSON (`JacksonJsonSerializer`, no type headers), keyed by ticket id so each ticket's events stay in order. Send failures are logged, never thrown: the request still succeeds, and the producer gives up after `max.block.ms=3000`. Events can be lost if the app dies between commit and send; there's no transactional outbox, by design for now.
- **Ticket history (Kafka consumer)** lives in the `activity` package. `TicketActivityListener` (`@KafkaListener`, group `helpdesk-activity`) stores each event in `ticket_activity` (V3). The table has plain `ticket_id`/`actor_id` columns with **no foreign keys**, because it's owned by the consumer, plus `details` as `jsonb` via `@JdbcTypeCode(SqlTypes.JSON)`. Processing is **idempotent**: an `existsByEventId` check, backed by a unique `event_id`, makes redeliveries and replays (offset resets) harmless. Consumer config is in `application.properties`: `ErrorHandlingDeserializer` wrapping `JacksonJsonDeserializer` with default type `TicketEvent`, no type headers, and `auto-offset-reset=earliest`. `KafkaConsumerConfig` adds a `DefaultErrorHandler` (2 retries, 1s apart, then log and skip). `GET /api/tickets/{id}/activity` (`TicketActivityService`) reuses `TicketService.get` for visibility and is **eventually consistent**. The UI's History section reloads it right after a change and again 1.5s later.

- **Search (Elasticsearch)** lives in the `search` package.
  - `TicketSearchIndexer` is a second `@KafkaListener` (group `helpdesk-search`). It treats each event only as a trigger: `TicketSearchService.index(ticketId)` re-reads the ticket and its comments from Postgres and saves a `TicketDocument` (a record; English-analyzed `title`/`description`/`comments`, keyword `status`/`priority`, `reporterId`) to the `tickets` index, or deletes it if the ticket is gone. That makes indexing idempotent and order-independent.
  - `@Document(createIndex = false)`: the app creates the index and mappings itself in `ensureIndex()`, at startup (a failure only warns) and before the first save or search. So a missing Elasticsearch never blocks startup, and documents are never saved under guessed mappings.
  - `GET /api/tickets/search?q=` builds a `NativeQuery` on `title^3`, `description`, `comments` with two `should` clauses (`minimum_should_match: 1`): a fuzzy `multi_match` (`fuzziness: AUTO`, for typos) and a `bool_prefix` `multi_match` (the last word matches as a prefix, so "print" finds "printer"; the English analyzer keeps "printer" and "print" as separate terms). Customers also get a `reporterId` term **filter**. Check analyzer behaviour with `curl localhost:9200/tickets/_analyze -d '{"field":"title","text":"..."}'` before relying on stemming. Highlights are wrapped in the private-use characters `MARK_START`/`MARK_END` (``/``), never HTML. Ids from Elasticsearch are loaded from Postgres (`TicketRepository.findByIdIn`) in ranking order, re-checking customer ownership.
  - Elasticsearch failures become `ServiceUnavailableException` (503). `management.health.elasticsearch.enabled=false` keeps `/actuator/health` UP without it. `POST /api/admin/search/reindex` (ADMIN) rebuilds the index from Postgres in pages of 100.

- **AI features (Amazon Bedrock)** live in the `assist` package, all AGENT or ADMIN only (`AssistController`):
  - *Assist:* `POST /api/tickets/{id}/assist` returns `AssistResponse(summary, suggestedReply, sources)` (`TicketAssistService`, on demand). It's **RAG**: the ticket's title and description are searched in the knowledge base (`KnowledgeBaseService.search`, top `MAX_ARTICLES = 3`), and those excerpts go into the prompt as escaped `<article id title>` blocks. The model's answer (`AssistAnswer`) lists `sourceArticleIds`; `sources()` keeps only ids that were really in the prompt (deduplicated) and adds titles. If the KB search fails, assist runs without articles.
  - *Triage:* a third Kafka consumer group, `helpdesk-triage` (`TicketTriageListener`), handles `CREATED` events only. `TicketTriageService` asks for `TriageAnswer(priority, category, reason)` and stores it in `ticket_triage` (V4; plain `ticket_id` column, unique, no FK, like `ticket_activity`). It's idempotent (`existsByTicketId` is checked before calling the model, so redeliveries don't cost anything), and it reads the ticket through `TicketService.find` (no ownership check, for background jobs). `GET /api/tickets/{id}/triage` returns it, or 404 until there is one. The suggestion never changes the ticket: staff apply it with the normal `PATCH` (so it appears in the history). Failures go to the shared Kafka error handler (2 retries, then skip: no suggestion). The group starts at `earliest`, so its first start triages existing tickets once.
  - Tickets have a nullable `category` (`Category` enum, V4), set only by staff (`UpdateTicketRequest.category`, event `CATEGORY_CHANGED` with `from: "NONE"` the first time), filterable with `?category=` (`TicketRepository.search`).
  - `BedrockJsonClient.ask(task, systemPrompt, userPrompt, schemaName, schema, recordType)` does every model call through Bedrock's **Converse API** (AWS SDK `bedrockruntime`, `BedrockRuntimeClient` bean in `AiConfig`). Converse has one request shape for every model, so the model is configuration only: `helpdesk.ai.model` / `HELPDESK_AI_MODEL`, default `qwen.qwen3-32b-v1:0`, region `helpdesk.ai.region` (default `us-east-2`). There's no API key: SigV4 with the default AWS credential chain (`AWS_PROFILE=helpdesk` locally, the ECS task role on AWS). Credentials are looked up on the first call, so the app and tests start without any.
  - **Structured output:** `outputConfig.textFormat` with each feature's `SCHEMA` (descriptions instruct the model; the triage schema's `enum` lists are generated from the Java enums). The answer is still parsed and checked: Bedrock *accepting* `outputConfig` doesn't mean the model obeys it (gpt-oss-120b returned invalid JSON, and Nova and Llama 4 reject the field). Only `stopReason == END_TURN` with valid JSON and every record field non-null counts; anything else (including an unknown enum value), and every `SdkException`, becomes `ServiceUnavailableException` (503). Each call logs model, stop reason and token counts.
  - The services are **not `@Transactional`**: they read through `TicketService` (short transactions), then call the model without holding a DB connection.
  - **Usage ledger** (V6 `ai_usage`, `AiUsageService`): every Bedrock call takes an `AiCaller(feature, userId)` (`AiFeature`: ASSIST, TRIAGE, AGENT, KB_SEARCH, KB_INDEX; userId null for background work) and writes one row with its tokens, recorded **before** the answer is checked (cut-off or invalid answers are billed too). A failed write only logs. `GET /api/admin/ai/usage?days=7` (ADMIN, `AiUsageQueries` with `JdbcClient` SQL, UTC days) gives totals per day/feature/model and the top 10 users, with an estimated cost from `helpdesk.ai.pricing.models[<model id>]` (USD per million tokens, from the AWS Pricing API; escape `:` as `\:` in `.properties` keys). Models without a price count as 0 and are listed in `unpricedModels`.
  - **Budgets** (`AiBudget.check(caller)`, called before every Bedrock call in `BedrockJsonClient`, `EmbeddingClient` and each agent loop step): a global daily cost cap (`helpdesk.ai.budget.daily-cost-usd`, default $1, today's ledger priced with `AiPricing`) and a daily token budget per user by role (`<role>-daily-tokens`: customer 10,000, agent and admin 1,000,000; `AiCaller` carries the role). UTC days; soft limits (checked before a call, no locking). Over a limit: `TooManyRequestsException` → **429** ProblemDetail with `Retry-After` (seconds to midnight UTC). Triage catches it and skips the ticket (no Kafka retries); saving a KB article still succeeds (not searchable until re-embedded); inside the agent, a tool hitting it becomes a tool error. Customers matter most here: sign-up is public, and every KB search is an embedding call.
  - **Resilience** (Resilience4j, `resilience4j-spring-boot4`, used programmatically through its registries, not annotations): `BedrockCircuitBreakers.call(model, ...)` wraps only the Bedrock call itself in a circuit breaker **per model id** (created on first use from `resilience4j.circuitbreaker.configs.default`: last 10 calls, at least 5, 50% failed → open 30s → 2 test calls). Only `SdkException` counts; answer validation happens after the call, so a bad answer never trips it. Open → 503 at once. Its health indicator is off on purpose: an open breaker must not make `/actuator/health` DOWN, or the ALB would stop every task during a Bedrock outage. The agent has a **bulkhead** (`resilience4j.bulkhead.instances.agent`: 4 concurrent questions, no waiting) around the whole `ask()` loop, because each question holds a platform request thread for 5–30s; a 5th gets 503 "busy". `HelpdeskApplicationTests` checks that both configs really reach the registries. Order per call: budget → breaker → SDK retries/timeout.
  - Ticket text is untrusted: it's put in XML-style tags with `<>&"` escaped (`PromptText.escape`), the system prompt says to treat it as data, and the result is only a draft an agent edits ("Use this reply" fills the comment box in the UI).
- **AI agent** (`agent` package; external MCP tools: see MCP client below): `POST /api/agent/ask` `{question}` (AGENT or ADMIN) returns `AgentResponse(answer, steps, modelCalls, inputTokens, outputTokens)`; each step is one tool call (`tool`, `input` JSON, `error`).
  - `AgentService` runs a hand-written **tool-use loop** on the Converse API: send the question and the tool list, and while `stopReason == TOOL_USE` run every `toolUse` block and send **all** results back in **one** user message (each with its `toolUseId`; failures use `status: ERROR`, so the model can recover). The text at `END_TURN` is the answer. `MAX_MODEL_CALLS = 6`, then 503. The model's messages go back into the history unchanged. Input tokens grow per call, because the whole conversation is resent every time.
  - Tools are `AgentTool<I>` beans (`agent.tools`: `list_tickets`, `search_tickets`, `get_ticket`, `find_users`, `search_knowledge_base`), all **read-only**, and they **run as the logged-in user** through the normal services, so the agent can't see more than that person. Each declares a JSON schema (enum values generated from the Java enums) and an input record; Bedrock's `Document` input is converted with `Documents` and Jackson (a bad input is an error result). Results are compact records (`TicketSummary`) to save tokens. To add a tool, add a `@Component`.
  - The system prompt (with the user and today's date) was tuned against real failures: inventing facts about tickets it hadn't opened, guessing user ids instead of calling `find_users`, announcing "I will look this up" and then stopping, and Markdown in a plain-text UI. Keep those rules. How-to and policy questions must be answered from `search_knowledge_base`, naming the article, never from general knowledge.
  - The agent uses its own model, `helpdesk.ai.agent-model` / `HELPDESK_AI_AGENT_MODEL` (default `qwen.qwen3-235b-a22b-2507-v1:0`). Qwen3 32B is fast (about 2 s) but stopped short on multi-step questions; 235B is reliable but takes about 5–30 s, hence CloudFront's `origin_read_timeout = 60`.
  - Tool execution lives in `AgentToolRunner` (lookup by name, input record conversion with Jackson, and the rule that only our own exceptions' messages reach the model; anything else is logged and reported as an internal error). It returns `Result(output, error)`, shared by `AgentService` and the MCP server.
  - Anthropic models are **not usable in this AWS account yet**: the use-case form and agreement are done, but invocations still return 403 "not available for this account" (an AWS-side restriction; a support case is the fix). Switching to Claude later is only `HELPDESK_AI_MODEL` / `HELPDESK_AI_AGENT_MODEL` plus the IAM resources in `infra/`.
- **MCP server** (`mcp` package, Spring AI `spring-ai-starter-mcp-server-webmvc`): the same `AgentTool`s for any MCP client (Claude Code, MCP Inspector) at `POST /api/mcp`, JSON-RPC (`tools/list`, `tools/call`). It's **stateless** (`spring.ai.mcp.server.protocol=STATELESS`: no MCP session in memory, like the JWT auth, so it works behind the ALB), offers tools only, and the annotation scanner is off.
  - Auth is the normal bearer token. `/api/mcp` is a router function, not a controller, so its role rule (AGENT/ADMIN) is a URL rule in `SecurityConfig`, before `/api/**`.
  - `McpServerConfig` replaces Spring AI's `WebMvcStatelessServerTransport` bean to add a **context extractor** that copies the `HelpdeskUserDetails` from the request into the `McpTransportContext`. Handlers read the user from there, not from `SecurityContextHolder`: they're on the request thread only because Spring AI sets `immediateExecution` for servlet apps (the SDK's default is a Reactor worker thread).
  - Each tool is a `SyncToolSpecification` (name, description, schema from the `AgentTool`, `readOnlyHint`). The SDK validates arguments against the schema before the handler runs. Tool failures are results with `isError: true`, not JSON-RPC errors. Clients must send `Accept: application/json, text/event-stream`.
  - Try it: `npx @modelcontextprotocol/inspector --cli http://localhost:8080/api/mcp --transport http --header "Authorization: Bearer <token>" --method tools/list`. A 401 makes MCP clients try OAuth discovery, which we don't offer, so an expired token (or a dev restart, which changes the random JWT key) shows up as an OAuth error.
- **MCP client** (`agent.ExternalMcpTools`, Spring AI `spring-ai-starter-mcp-client`): the agent also uses tools from external MCP servers, configured as `spring.ai.mcp.client.streamable-http.connections.<name>` (now `aws-knowledge`: AWS's public documentation server at `https://knowledge-mcp.global.api.aws`, endpoint `/`, no credentials). Our MCP server doesn't re-offer them (`expose-mcp-client-tools=false`).
  - **Allowlist:** only tools named in `helpdesk.agent.mcp-tools` (`AgentProperties`, default none) are offered: now `aws___search_documentation`. `read_documentation` is left out on purpose, because whole pages cost thousands of tokens on every later call. Results are cut at `MAX_RESULT_CHARS = 8000`. External descriptions are prefixed `[External: <connection>]` in the Bedrock tool list, and the prompt's rules for them refer to that.
  - **Resilience:** `spring.ai.mcp.client.initialized=false`, so there's no connection at startup (a down server would otherwise stop the app). The first `listTools` does the handshake, and a failed one is retried. Tool lists are cached for 10 minutes; a failing server is skipped for 1 minute (one warning) and the agent carries on with its own tools. `request-timeout=10s`.
  - **Data egress lock** (`AgentService`): external tools get only the model's input, never the user, and that input leaves the company. Once a question has used one of our tools (in an earlier turn; calls in the same turn haven't seen any results), external calls are refused with `EXTERNAL_LOCKED`. This is enforced in code because the prompt rule ("no customer data in external inputs") failed in real tests: asked directly, Qwen sent a ticket's description and the customer's email to the AWS search. Keep the lock, and don't loosen it to a prompt-only rule.
  - Full-context tests set `spring.ai.mcp.client.enabled=false` (in both classes, to keep the shared context), so they never reach the internet; `ExternalMcpTools` then has no clients (`ObjectProvider`). On ECS the app reaches the server through its public IP and the all-egress security group rule, so no infra change was needed.

- **Knowledge base** (`kb` package): help articles that everyone logged in can read and search by meaning; AGENT/ADMIN write them.
  - Endpoints: `GET/POST /api/kb/articles`, `GET/PUT/DELETE /api/kb/articles/{id}`, `GET /api/kb/search?q=` (top 5), and `POST /api/admin/kb/reindex` (ADMIN, re-embeds everything, e.g. after changing the embedding model).
  - **Embeddings + pgvector** (V5): `create extension vector`. `kb_article` is a JPA entity; `kb_chunk` (`embedding vector(512)`, HNSW index with `vector_cosine_ops`, `on delete cascade`) is **not** an entity: `KbChunkStore` uses `JdbcClient` with plain SQL (vectors as `cast('[...]' as vector)`, ordered by `embedding <=> query`, cosine distance; similarity = 1 − distance).
  - `TextChunker` splits a body into chunks of up to 1000 characters, keeping paragraphs and sentences whole. `EmbeddingClient` (in `assist`) calls Amazon Titan Text Embeddings V2 through **`InvokeModel`** (not Converse) with `dimensions: 512, normalize: true`; `DIMENSIONS` must match the column. Each chunk is embedded **with the article title in front**, but stored without it.
  - `KnowledgeBaseService` (not `@Transactional`; embeds outside DB transactions): create/update save the article first, then embed it. If embedding fails, the article is still saved, with `chunkCount` 0 meaning not searchable (on update, the old chunks stay). Search embeds the query, takes the 20 nearest chunks, keeps the best per article, and drops anything below `MIN_SIMILARITY = 0.2`. That threshold was tuned on real Titan scores: right answers 0.30–0.48, unrelated about 0.10. Raw similarity isn't a percentage, so the UI shows it to staff only.
  - The same search feeds assist (RAG), the agent's `search_knowledge_base` tool, and the suggested articles on the new-ticket page.

**Tests**, in `src/test/java`, mirror the main packages:
- `*ServiceTests`: plain Mockito unit tests with no Spring context.
- `*ControllerTests`: `@WebMvcTest` with a `@MockitoBean` service and `MockMvcTester` (AssertJ style). They `@Import(SecurityConfig.class)` so the real rules apply (a slice test doesn't pick up `@Configuration` classes on its own), and run requests as a user with `.with(user(new HelpdeskUserDetails(...)))`.
- `*RepositoryTests` (and `KbChunkStoreTests`): `@DataJpaTest` with `TestEntityManager`, against Testcontainers Postgres. The image is `pgvector/pgvector:pg18-trixie`, the same as Compose, declared `asCompatibleSubstituteFor("postgres")`.
- `HelpdeskFlowTests` and `HelpdeskApplicationTests` also import `KafkaTestcontainersConfiguration`, `ElasticsearchTestcontainersConfiguration` (security off, 256 MB heap) and `FakeBedrockConfiguration`. The last is a `@Primary` mock `BedrockRuntimeClient` returning canned JSON chosen by schema name (for agent requests, which have a `toolConfig`: one `list_tickets` call, then a text answer; for `InvokeModel` embeddings, a normalized bag-of-words hash vector, so texts sharing words are "similar"), because every created ticket is triaged and tests must never reach real Bedrock (no credentials in CI, and it costs money locally). These are kept separate from the Postgres config so `@DataJpaTest` doesn't start them. The two classes have **identical annotations on purpose**, so Spring's test context cache shares one context and one set of containers; keep them in sync, or test time roughly doubles. Search assertions use Awaitility, because indexing is asynchronous. `HelpdeskFlowTests.readEventTypes` reads the topic with a throwaway consumer group to assert published events.
- `HelpdeskFlowTests`: end-to-end `@SpringBootTest` + `@AutoConfigureMockMvc` tests with nothing mocked. Users register, log in at `/api/auth/login` for real, and send the bearer token (the `login(...)` helper returns a `RequestPostProcessor`). Controllers that need `TokenService` (`AuthController`) get it as a `@MockitoBean` in slice tests.

In Spring Boot 4 the test annotations live in per-module packages, e.g. `org.springframework.boot.webmvc.test.autoconfigure.WebMvcTest` and `org.springframework.boot.data.jpa.test.autoconfigure.DataJpaTest`.

## Frontend

`frontend/` is a React 19 + TypeScript SPA built with Vite 8 and React Router 8, with no UI library and hand-written CSS in `src/index.css`. Run commands from `frontend/`:

```bash
npm install          # after cloning or when package.json changes
npm run dev          # dev server on http://localhost:5173, proxies /api to localhost:8080 (backend must be running)
npm run build        # type-check (tsc --noEmit) + production build into frontend/dist
```

- `src/api.ts`: every backend call goes through `api<T>(path, {method, body})`. It adds the bearer token from localStorage (`helpdesk.token`), throws `ApiError` carrying the ProblemDetail (`problem.errors` holds field errors) for non-2xx responses, and clears the token and logs out on a 401 for an authenticated request. A 204 resolves to `undefined`.
- `src/auth.tsx`: `AuthProvider` / `useAuth()` hold the current user (`undefined` while a saved token is checked with `/users/me`, `null` when logged out) and `login`, `register`, `logout`.
- `src/App.tsx`: routes. Pages that need a login sit under `RequireAuth` and use `components/Layout`. Routes are `/` (ticket list: "My tickets" for customers, filterable queue for staff), `/tickets/new` (when the title or description loses focus, `SuggestedArticles` searches the KB and links up to 3 articles, opened in a new tab so the draft survives; it shows nothing on no match or error), `/tickets/:id` (detail, comments, and staff-only parts: the AI triage card with an Apply button (a 404 from `/triage` means "not yet"), status/priority/category/assignee controls, and the AI assistant panel with "Based on:" links to its source articles), `/ask` (staff only, behind `RequireStaff`: the AI agent; `#12` in answers becomes a `<Link>` by splitting the text, never as HTML, and a collapsible list shows the tool calls), and `/kb`, `/kb/:id` (knowledge base for everyone; search runs on submit, not while typing, because each search costs an embedding call, and `?q=` is in the URL), `/kb/new` and `/kb/:id/edit` (staff), and `/users` (admins only, behind `RequireAdmin`: create users with any role, and change roles through a per-row select that saves on change; your own row is disabled). `Layout` shows Tickets and Users (admin) `NavLink`s.
- `src/useApi.ts`: `useApi<T>(path)` loads data for a component (`{data, error, reload}`) and ignores stale responses. Use it for GETs; writes call `api()` directly and then `reload()`.
- Search: the ticket list's `SearchBox` debounces typing (300 ms) into `?q=` (with `replace`, so typing doesn't add history entries). While `q` is set, `SearchResults` (ranked, from `/tickets/search`) replaces the filters and table. `components/Highlighted` renders backend snippets by splitting on ``/`` into `<mark>` elements. **Never render search highlights or ticket text with `dangerouslySetInnerHTML`**: ticket content is user input.
- List filters (status, and for staff assignee and category) live in the URL query (`useSearchParams`), not component state. Staff-only data (`/users`) is fetched in staff-only child components, because customers get 403 for it.
- `src/types.ts` mirrors the backend's response records. Update it when a DTO changes.

**How the UI is served:** in development, Vite (port 5173) serves the UI and proxies `/api`. In the Docker image, a `node:24-alpine` stage runs `npm ci && npm run build`, and the JDK stage copies `dist/` into `src/main/resources/static/` before `./mvnw package`, so the jar contains the UI and serves it on 8080 alongside the API. That folder is git-ignored and only populated inside the Docker build; a plain `./mvnw spring-boot:run` serves no UI. `SpaWebConfig` returns real static files, and returns `index.html` for any other non-`api/` path, so React Router deep links survive a reload. `SecurityConfig` requires authentication for `/api/**`, ADMIN for `/actuator/**` (except health), and permits everything else (the static UI). `src/test/resources/static/index.html` is a stand-in so `HelpdeskFlowTests` can test this.

## Commands

```bash
docker compose up -d                   # start Postgres + Kafka + Elasticsearch (required before running the app)
docker compose down                    # stop them (data kept in the pgdata/kafkadata/esdata volumes; add -v to wipe)
curl -s localhost:9200/tickets/_search?pretty                                 # look at the search index directly
docker compose exec kafka /opt/kafka/bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 \
  --topic helpdesk.ticket-events --from-beginning --property print.key=true   # watch ticket events
docker compose exec kafka /opt/kafka/bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 \
  --describe --group helpdesk-activity                                        # consumer offsets and lag
./mvnw spring-boot:run                 # run the app (port 8080 by default)
HELPDESK_ADMIN_EMAIL=admin@example.com HELPDESK_ADMIN_PASSWORD=admin-password ./mvnw spring-boot:run  # same, with a bootstrap admin
./mvnw test                            # run all tests
./mvnw test -Dtest=TicketControllerTests              # run a single test class
./mvnw test -Dtest=TicketServiceTests#updateAssignsTicketToAgent  # run a single test method
./mvnw clean package                   # build the jar into target/
docker compose --profile app up -d --build   # build the image and run app + Postgres in containers
docker compose --profile app down            # stop both (plain `down` leaves the app container running)
```

The `app` Compose service uses a profile, so plain `docker compose up -d` starts only Postgres for `spring-boot:run` development. Set `APP_PORT=18080` to publish the containerized app on another host port.

The [Dockerfile](Dockerfile) is multi-stage. The Node and JDK stages use `FROM --platform=$BUILDPLATFORM`, so cross-building (ARM64 on CI's x86 runner) only emulates the final JRE stage. A Node stage builds the React UI (see Frontend), then a JDK stage runs `./mvnw package -DskipTests` (tests need Docker, which isn't available inside a build) with a BuildKit cache mount for `~/.m2`, then extracts Boot's jar layers (`-Djarmode=tools extract --layers --launcher`). The JRE stage copies the layers in order, from least to most frequently changing, runs as the non-root `spring` user, and starts with `JarLauncher`. Inside Compose the app reaches the database through `DB_URL=jdbc:postgresql://postgres:5432/helpdesk` (the service name, not `localhost`).

**CI** ([.github/workflows/ci.yml](.github/workflows/ci.yml)) runs on pushes to `main` and on pull requests. `backend` runs `./mvnw -B verify` (Testcontainers uses the runner's Docker) and uploads the surefire reports on failure. `frontend` runs `npm ci && npm run build`. The backend tests start Postgres, Kafka and Elasticsearch containers on the runner. `docker` (pull requests only) builds the image without pushing it (GitHub Actions layer cache), and only runs after both pass. `deploy` (pushes to `main` only, after both pass) is the CD: it assumes the IAM role `helpdesk-github-deploy` through GitHub OIDC (`id-token: write`; the role's trust policy only accepts `repo:pbhagat22@235375028/helpdesk@1418245817:ref:refs/heads/main`, GitHub's immutable subject format with owner and repo IDs, no AWS keys in GitHub), builds `linux/arm64` with QEMU, pushes `helpdesk:<7-char sha>` to ECR, and, only if the ECS service `app` is ACTIVE, registers a task definition revision with the new image, updates the service and waits for `services-stable`. Deploys run one at a time and are never cancelled midway. Check runs with `gh run list` / `gh run view --log-failed`. The repo is public: Actions minutes, rulesets and CodeQL are free, and everything committed is world-readable, so never commit real secrets.

No linter or formatter is configured. Tests need Docker running (OrbStack is installed), but not `docker compose`. Testcontainers starts its own Postgres.

## AWS (roadmap stages 7–8)

Built by hand in stage 7, now managed by Terraform in [infra/](infra/) (state in S3 bucket `helpdesk-tfstate-936303390305`, native S3 locking). [infra/README.md](infra/README.md) has the commands. Change AWS resources through the `.tf` files, not the console or CLI, or the next plan will try to revert them.

- **Account and access:** the sign-up created an AWS Organization. The work happens in member account "Try Catch Finally" (936303390305), not in the management account. An organization SCP **denies every region except us-east-2**. The CLI profile `helpdesk` is IAM user `pbuser1` with an access key (`aws login` failed with this sign-up's federated setup). The provider's `allowed_account_ids` refuses any other account. The user runs `terraform apply` and other AWS-changing commands themselves; Claude verifies with read-only commands and `terraform plan -lock=false`.
- **Costs:** resources that bill hourly (RDS, ECS services, ALB, Cloud Map namespace) only exist while `var.running` is true (`count`/`for_each`): `terraform apply -var running=true` brings them up, and `terraform apply -var running=false` **tears them down at the end of every session**. `running` has no default on purpose, so every plan/apply must pass it (verify with `terraform plan -lock=false -var running=<current state>`). Never `terraform destroy`. The rest stays: ECR (`prevent_destroy`), IAM role, security groups, DB subnet group, cluster, task definitions, log group and the CloudFront distribution. The SSM parameters are created by hand and never managed by Terraform, so secret values stay out of the state; RDS gets its password from an `ephemeral "aws_ssm_parameter"` through the write-only `password_wo`.
- **ECR** repository `helpdesk` has immutable tags (git short sha), a lifecycle policy keeping 5 images, and a registry-wide BASIC scan-on-push rule (the repository-level `scanOnPush` flag isn't honoured). Push a plain single-arch image (`docker build --platform linux/arm64 --provenance=false --sbom=false`, see infra/README.md); without the attestation flags, Docker pushes an image index plus a provenance manifest, which breaks scanning by tag and the lifecycle count. Terraform's app task definition uses the most recently pushed image (`data "aws_ecr_image"` with `most_recent`), so a bring-up always starts the latest build. While running, the deploy job owns the service's task definition (`ignore_changes = [task_definition]` on `aws_ecs_service.app`); the next apply after a deploy shows the task definition replaced with the new tag, which is expected.
- **Architecture:** CloudFront (HTTPS, `https://d1fpqs2kiuwucp.cloudfront.net`, caching off, all headers but `Host` forwarded) → ALB (HTTP; its security group only allows CloudFront's managed prefix list) → ECS Fargate ARM64 service `app` (0.5 vCPU / 2 GB) in the default VPC's public subnets, with public IPs and **no NAT gateway**. While not running, CloudFront's origin is the placeholder `helpdesk-offline.invalid` (502).
  - **Kafka and Elasticsearch** (`apache/kafka`, `elasticsearch`) run as their own Fargate services, reached as `kafka.helpdesk.local:9092` and `elasticsearch.helpdesk.local:9200` through Cloud Map DNS. Kafka advertises that name. Their data isn't durable, which the design tolerates: Postgres is the source of truth, and search can be rebuilt with `/api/admin/search/reindex`.
  - **RDS** Postgres 18 `db.t4g.micro` is private, single-AZ, with no backups, and is reachable only from the app's security group. Its endpoint is stable across recreation, so it's fixed in `infra/ecs.tf`.
  - **Secrets** (`/helpdesk/db-password`, `jwt-secret`, `admin-password`) are SSM SecureStrings, injected by the task execution role through the task definition's `secrets` section. The admin is `admin@example.com`.
  - **Task role** `helpdesk-app-task` is what the app code runs as. It may only `bedrock:InvokeModel` on `local.ai_model` and `local.ai_agent_model` (`infra/ecs.tf`, also passed as `HELPDESK_AI_MODEL` / `HELPDESK_AI_AGENT_MODEL`). The deploy job's `jq` keeps `taskRoleArn` when it copies the task definition, and the deploy role may `iam:PassRole` both roles.
  - **Logs** go to CloudWatch `/ecs/helpdesk`.

## Kubernetes (roadmap stage 10)

A local cluster with [kind](https://kind.sigs.k8s.io/) on OrbStack, defined in [k8s/](k8s/) and put together by Kustomize ([k8s/kustomization.yaml](k8s/kustomization.yaml)). Always apply the whole folder (`kubectl apply -k k8s`, preview with `kubectl diff -k k8s`), never single files: the namespace, labels, image tag and Secrets only come from the kustomization.

- **Cluster:** `kind create cluster --config k8s/kind-config.yaml` makes one node named `helpdesk` (kubectl context `kind-helpdesk`). There's one node only, because the Mac has 8 GB and OrbStack's VM about 4 GB. Port mappings can only be set at creation: the app's NodePort 30080 is published as `http://localhost:30080`. metrics-server (v0.8.0 manifest, patched with `--kubelet-insecure-tls` for kind's self-signed kubelet certificate) gives `kubectl top`. `docker stop/start helpdesk-control-plane` pauses the cluster with its data; `kind delete cluster --name helpdesk` deletes everything. Stop the Compose stack (`docker compose stop`) while the cluster runs, for memory.
- **Postgres, Kafka, Elasticsearch** are StatefulSets with headless Services (`postgres:5432`, `kafka:9092`, `elasticsearch:9200`) and a 1 Gi PersistentVolumeClaim each (kind's local-path provisioner). Kafka has one listener advertised as `kafka:9092`, heap 256 MB, `enableServiceLinks: false` (the image turns every `KAFKA_*` variable, including Kubernetes' `KAFKA_PORT=tcp://...`, into a broker setting), and a `tcpSocket` probe (a probe running Kafka's client script would start a second JVM inside the memory limit). Elasticsearch has heap 256 MB and no init container: OrbStack's kernel already has `vm.max_map_count=262144`.
- **App** is a Deployment with a NodePort Service. `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=50` overrides the Dockerfile's 75%, because the limit is 1 Gi (it uses about 550 Mi). Probes use Spring Boot's own groups, which it enables when it detects Kubernetes: a `startupProbe` (up to 3 min), then liveness `/actuator/health/liveness` (restarts; never checks Postgres or Kafka) and readiness `/actuator/health/readiness` (takes the pod out of the Service). A `preStop` sleep of 5 s (with `terminationGracePeriodSeconds: 45`) closes the race between SIGTERM and the Service update: without it, a rollout lost 2 of 400 requests; with it, 0. A change to shutdown behaviour only takes effect one rollout later, because the pod being stopped still has the old spec. There are no AWS credentials in the cluster, so Bedrock features answer 503 and triage gives up after its retries.
- **Image:** it exists only on the Mac, so build it and copy it into the node, then set the tag in `images: newTag` (`imagePullPolicy: IfNotPresent`; never use `latest`, which makes Kubernetes always pull from a registry):
  ```bash
  docker build --provenance=false --sbom=false -t helpdesk:<tag> .
  kind load docker-image helpdesk:<tag> --name helpdesk
  ```
  `kind load` fails for multi-arch images pulled from registries (`content digest ... not found`: Docker's containerd image store has only the arm64 layers, and kind imports `--all-platforms`), so third-party images are pulled by the node itself. During `docker build`, scale Elasticsearch to 0 (`kubectl scale statefulset elasticsearch -n helpdesk --replicas=0`; its volume is kept) so the build fits in memory. Roll back by changing the tag in the file, not with `kubectl rollout undo`, which the next apply would revert.
- **Secrets** come from `secretGenerator` (dev values, the same as `compose.yaml`). Names get a content hash (`app-<hash>`, `postgres-<hash>`) and references are rewritten, so a changed value rolls the pods. `apply` never deletes anything: an old Secret, or anything removed from the files, has to be deleted by hand.
- **Labels:** `app.kubernetes.io/part-of: helpdesk` goes on top-level objects only. `includeTemplates` would also label the StatefulSets' `volumeClaimTemplates`, which are immutable, so the apply fails.

## Configuration

Config lives in `src/main/resources/application.properties`. The app connects to Postgres 18 from `compose.yaml` (image `pgvector/pgvector:pg18-trixie`: Postgres plus pgvector, on the same Debian release as `postgres:18`, so an existing volume's collation matches; the plain `pg18` tag triggers a "collation version mismatch" warning) (database, user and password are all `helpdesk`). Override the connection with the `DB_URL`, `DB_USERNAME` and `DB_PASSWORD` environment variables. Kafka (`apache/kafka:4.2.1`, single-node KRaft) is at `localhost:9092` from the host, overridden with `KAFKA_BOOTSTRAP_SERVERS`. Inside the Compose network it's `kafka:29092`, because Kafka advertises a separate listener per network. Elasticsearch (single node, security off for dev, 512 MB heap) is at `http://localhost:9200`, overridden with `ELASTICSEARCH_URIS`, or `http://elasticsearch:9200` inside Compose. The SQL Hibernate runs is logged at debug level.

**Schema changes go through Flyway** (`src/main/resources/db/migration`, Postgres SQL). Hibernate runs with `ddl-auto=validate`, so it never changes tables, and startup fails if an entity doesn't match the schema. To change an entity's columns, add a new `V<n>__description.sql` migration alongside the entity change. Never edit a migration that has already been applied. Enum columns are `varchar(20)` with `@Column(length = 20)` and no check constraints. Foreign key columns used in queries get an explicit index, because Postgres doesn't index them automatically. To query the database directly: `docker compose exec postgres psql -U helpdesk -d helpdesk`.

Tests that need a database `@Import(TestcontainersConfiguration.class)`. Its `@ServiceConnection` Postgres container overrides `spring.datasource.*`, so tests never touch the Compose database. `@WebMvcTest` and plain unit tests don't need it.

When starting the app to test changes, check whether port 8080 is already in use (the user may have their own instance running). Use a different port, e.g. `-Dspring-boot.run.arguments=--server.port=18080`, and stop only the process you started.
